# LA-LagCheck 0.8.0

LA-LagCheck estimates laser/MS time-coordinate drift from block lags, checks whether a single time-axis correction is supported, and exports a separately verified laser log. When the timing checks fail, at the input diagnostic or at the read-back of the written file, `run --export` can still write a provisional corrected log, marked as not verified. It uses the rate estimated from the acquisition when that estimate is eligible for provisional export. Otherwise it uses a reference rate given with `--reference-rate-ppm`. Without an eligible estimate or a reference rate, no provisional log is written. It does not change MS intensities or the original input files.

## Run it once

Run these four commands from this package directory, the folder that holds this file. Use the same Python interpreter for all of them, and use Python 3.12: the pinned versions in `requirements-reference.txt` were validated with Python 3.12.5 and have no prebuilt packages for Python 3.13 or later. With another Python version, install `requirements.txt` instead; it gives version ranges, and not every combination in them was tested. Keep `-X utf8` in every command so Python and test-runner output use UTF-8. The command-line entry point also reconfigures standard output and error to UTF-8 at startup, so the program can print µ and superscript characters when output is redirected or piped on Windows under a legacy code page.

```text
python -X utf8 -m pip install -r requirements-reference.txt
python -B -X utf8 -m lagcheck --version
python -B -X utf8 -m pytest -p no:cacheprovider tests
python -B -X utf8 scripts/verify_package.py
```

What each command should show:

1. `pip` installs the pinned reference versions of NumPy, pandas, SciPy and matplotlib, and pytest for the tests. Its output contains a line that starts with `Successfully installed` followed by the package names, or `Requirement already satisfied` lines if they are present already. pip may add a notice about a newer pip version, which can be ignored. `requirements-lock.txt` lists every package of the environment in which this release was validated, with its indirect dependencies. It is a record and is not needed for installation.
2. The version number in the title of this file.
3. A last line that contains `341 passed, 1 skipped`. The same line counts 14 warnings in the reference environment; they come from matplotlib and are expected. The run took about three minutes on the development computer. The skipped test needs an optional private fixture that is not distributed.
4. `"status": "verified"` and an empty `differences` list. The script compares the files with the hashes recorded in `FILES.json`.

The tests create their temporary folders in the system temporary directory. `-B` and `-p no:cacheprovider` stop Python and pytest from writing cache folders into the package directory.

`python -B -X utf8 -m unittest discover -s tests -v` also runs once pytest is installed. It ends with `Ran 323 tests` and `OK (skipped=1)`, which is 322 passed and 1 skipped. Its count is lower than that of pytest because unittest does not collect the 17 function-style test cases of `tests/test_new_wave_short.py`. With `-q` added to the pytest command above, its last line also reports `118 subtests passed`. Without `-q`, the last line of pytest 9.1.1 does not give the number of subtests.

## Behaviour and version notes

The program screens the laser log (added in 0.6.0). The screen compares each line-change interval (the logged start of firing minus the logged end of the preceding firing) with the median of up to five neighbouring intervals on each side. An interval is flagged when it differs by more than `line_change_limit_s` (default 1 s) and by more than ten times the scaled median absolute deviation of those neighbours; the second condition reduces flagging caused by ordinary variation in irregular sequences, such as spot acquisitions. A flag marks a line-change interval that is unusually long or short relative to its neighbours. It may reflect an acquisition pause, a timestamp step or variation in the acquisition sequence, and the log alone does not establish the cause. The block lags do not test an interval that lies inside an unusable block. The screen is therefore reported as the check `no_flagged_line_change_interval`: a flagged interval withholds supported status and leaves any estimated rate available. The report lists every flagged interval under `laser_log_screen`, including when a prerequisite stops the diagnosis. `python -B -X utf8 -m lagcheck screen-log config.json` screens the laser log named in a run configuration without reading a signal file (exit 0 when no interval is flagged in the evaluated segments, 2 when an interval is flagged or nothing could be evaluated; `unevaluated_segments` counts segments that were too short to screen). Steps smaller than the limit are not detected by the screen. Intervals that recur by design, such as bracketing standards, are flagged. Groups of similarly displaced adjacent intervals can escape detection because they shift the local reference. A changed limit is written to the report and to the manifest of any exported log, together with the number of intervals that the default limit would flag.

`analysis.skip_record_edge_lines` (default `true`, since 0.7.0) concerns the scan lines at the start or end of the signal record. In routine records the signal often begins as the first line is fired, so the lag search of the first block cannot extend before the record and its correlation peak can lie at that search boundary, which fails the search-edge check. The diagnosis first uses every scan line. If a block's peak lies at a search boundary imposed by the start or end of the signal record (in the initial fit, the iterated fit or any stability alternative), the whole diagnosis is repeated without the scan lines that start within 30 s of the first recorded sample, or end within 30 s of the last. The value 30 s is the largest lag-search half-width used in the checks. The neighbouring lines and the laser-off intervals between lines provide the missing signal on both sides. The same lines are left out of every fit of the repeated diagnosis, and they are left out only if at least twelve lines per block remain. Coverage is still measured against all lines. The report lists the outcome under `record_edge_lines` (`enabled`, `applied`, `sides`, `skipped_at_start`, `skipped_at_end`, `guard_s`, `rule`). If no peak lies at such a boundary, nothing is left out and the result equals that of `"skip_record_edge_lines": false`, which restores the earlier behaviour.

`analysis.exclude_record_boundary_blocks` (default `false`) concerns blocks at the start or end of the signal record, most often the first block of a record that starts as the signal of the first firing arrives. A record-boundary block has its lag search cut short by the start or end of the signal record and its correlation peak within two sampling intervals of that shortened boundary. `record_boundary_blocks` in the report lists such blocks of the reported fits and of the stability alternatives under either policy. By default the search-edge check applies to them; the automatic omission of edge lines described above is the first remedy, and this option is the declared alternative when the check is still not met. With the option, a fully observed record-boundary block that would otherwise enter the fit leaves the fit and the coverage but must still agree with the fitted line within the tolerance. This agreement uses the measured peak near the boundary of the observable search range. It can show a lag inside the record but not a lag beyond the record boundary, which is the case the search-edge check guards against by default. The option therefore assumes that the record contains the signal of the excluded block; the report gives the peak of that block beside the median peak of the retained blocks. If the option excludes a block in any reported fit or stability alternative, a passing result has status `supported_excluding_record_boundary_blocks`, exits 2 and can publish only a provisional log. With the option set and no block excluded, the result is unchanged.

`ms.signal_selection` (since 0.7.0 `"highest_alignment_peak"` by default for the CSV signal formats; netCDF input keeps `"sum"`) compares the configured sum and each configured column by the peak of the automatic starting-alignment search around the input placement and uses the candidate with the highest peak. The sum is kept unless a single column exceeds it by more than 1e-9. With a single configured column there is nothing to compare. `"sum"` can still be requested explicitly and then uses the sum of the configured columns. The search is the automatic one even when a starting alignment is declared, and a candidate can win on peak height without meeting the starting-alignment criteria; the report records both facts. The report records every candidate under `signal_selection`, and the saved `config.json` names the columns actually used. These defaults and the option are declared choices made from the same record. They were defined after the default outcomes of the 28 saved-workspace acquisitions (R01 to R28) had been examined, so the number of acquisitions that pass with them is retrospective and not a prospective success rate. In the validation of 0.7.0, with both 0.7.0 defaults switched off (`"skip_record_edge_lines": false` and `"ms.signal_selection": "sum"`), all 81 comparison runs (R01 to R28 under automatic and declared starting alignment, 56 runs; the corrected inputs of R05, R07 and R14 under both alignments, 6 runs; three settings for R29; and 16 settings for the two clock-comparison scans) equalled the 0.6.0 default results. That comparison was made with 0.7.0, when these defaults were introduced. The `config.json` written by a run names the columns that were actually used and sets `ms.signal_selection` to `"sum"`, so rerunning that file uses the same matching signal.

The program draws `preview_pair.png` and `preview_pair.json` by default for `run` and `wizard`, including unsupported diagnoses and failed read-backs. `--no-preview` explicitly disables drawing. `--no-sample-label` leaves the sample label of the laser log out of the title of `preview_pair.png`; without the switch the title is unchanged. The figure states the input diagnostic, read-back and export stages separately. Published log bytes and their fixed timing mapping take precedence over the current estimated rate; a single-pass baseline is never substituted for an iterated exported log. Without an estimated or user-supplied reference rate, it shows the original or explicitly declared alignment. The figure and the log read one record of the mapping in use (`provisional_export_eligibility.applied_mapping` in `report.json`). A rate that is withheld from the provisional log is therefore not drawn as an applied correction. The estimate then appears in a separate panel whose title starts with `rejected candidate for inspection`, beside the original or declared alignment and, when a reference rate was supplied, beside that rate. Missing geometry uses line order and time; diagonal or mixed trajectories also use this nonspatial view. No interval coverage produces a raw signal timeline. Oversized grids use a recorded larger pixel pitch and average contributing intervals; they are inspection previews, not full-resolution images.

When starting alignment is not declared, an unidentifiable automatic start can trigger a separate retry at the original input placement. An automatic rate that fails block agreement or held-out prediction (including their iteration-stage checks) also triggers this retry. It uses the same signal and settings, setting the input-placement offset to zero, with each fragment's original origin shift retained. The candidate is adopted only with a finite rate, positive time scale, and explicitly passing agreement and prediction at both initial-fit and iteration stages. Convergence is reported but is not an additional adoption gate. Top-level strict diagnostic fields stay unchanged; the candidate is recorded under `alignment_fallback` and in `alignment_fallback_report.json` and its block files. Adoption is always provisional, even if read-back passes, and exits 2. Adopted candidates take precedence over the original estimate and a reference rate. A rejected retry retains the original candidate or reference under the existing rules and records its rejection. `--no-alignment-fallback` disables retry; `--no-provisional` disables retry and provisional logs; `--no-preview` only disables drawing. Without `--export`, retry can still supply a preview but no log. See [TROUBLESHOOTING.md](TROUBLESHOOTING.md) for the input-placement assumption and explicit next steps.

Since 0.8.0, a rate estimated from the acquisition is written to a provisional log only when it is eligible for provisional export. `provisional_export_eligibility` in `report.json` records this for the diagnostic that an export uses: the adopted retry at the input placement, otherwise the main diagnostic. There are three conditions: the direction of the single-pass rate is uncertain; the rates of the alternative settings differ in sign; the iteration did not converge and the rate still changes. A condition withholds the estimate only when the lag change that it amounts to over the firing span exceeds the tolerance of the run. `status` is `not_blocked`, `withheld`, `not_assessable` or `no_acquisition_rate`, and `evidence_completeness` is `complete` or `incomplete`. `not_blocked` means only that none of the three conditions was triggered; the failed checks and the missing estimates still apply. The eligibility restricts provisional output only. It changes no rate, check, status or exit code, and a supported result is still exported through the verified path. A withheld estimate stays in the report with its failed checks. A reference rate, if one was given with `--reference-rate-ppm`, is then written instead, as a rate-only mapping that takes no fitted constant from the estimate. The eligibility, the tolerance and the alternative settings that gave no rate are written to `report.md` and to the `provisional_manifest.json` of a provisional log. The preview of a result that is not supported states them in its footer. See [TROUBLESHOOTING.md](TROUBLESHOOTING.md) for the three conditions and for what a provisional log can be used for.

`analysis.tolerance_s` has no default and must be given. The tolerance can be given as a distance along the scan instead (since 0.8.0), with `analysis.tolerance_um` or `--tolerance-um`. It is converted to seconds once, before the diagnosis, with the largest scan speed of the valid firing intervals, and `tolerance_resolution` in `report.json` records the request, the speed, its source and the resolved seconds. The estimator, the checks and the read-back receive seconds only, so the same seconds give the same result however they were requested. `--tolerance-s` and `--tolerance-um` replace the tolerance of the configuration for one run. A distance request is an input error when a scan speed is neither usable for every firing interval nor declared, for spot records and for New Wave logs; a tolerance in seconds is accepted for all of them. Where a scan speed is known, `distance_scale` in `report.json` gives the time differences of the diagnosis as distances along the scan. Spot widths are given only when the width of the spot along the scan is declared (`analysis.spot_width_along_scan_um`) or recorded without ambiguity.

The default run reader excludes exactly zero-duration firing pairs from analysis and records their original 1-based CSV data-record numbers in `input_processing.json`. Negative durations, overlapping or incomplete events remain errors. Original files are read-only. Excluded zero-duration event rows remain in any timestamp-corrected CSV; `output_config.zero_duration_policy=exclude` makes the program's read-back apply the same exclusion. This is not a claim that another importer treats those rows identically.

For the generic laser-state adapter, disconnected selected-sample or sequence fragments are diagnosed separately under `segment_001/`, etc., with a `segments.json` index and a root raw-signal overview. No gap is bridged and no logs are combined. The original MS time axis is retained; a declared offset is adjusted by each fragment's recorded origin shift. A fragment containing only Off metadata is recorded as `no_firing_fragment`, without inventing another sample image. Multiple samples require an exact selector in that generic adapter. The explicit New Wave adapter instead interprets Sequence Number as a line/spot identifier. Its exact named-sample selection can omit interleaved standards within the explicitly paired input file, retaining source gaps and original firing times without combining firing intervals. New Wave sample_scope=all explicitly includes all labels; neither mode invokes the generic per-sequence splitting rule.

`original_input_check` records whether the original records required processing; `processed_input_diagnostic_status` records the unchanged estimator's result on the retained fragment. When exclusion or segmentation was required, a supported processed result has status `processed_input_diagnostic_supported` and can publish only a provisional log (exit 2). It does not upgrade the original input to verified. Clean original inputs retain the two-stage verified export. The reference correlation core is unchanged in executable code; one comment in it was reworded in 0.6.0. Since 0.6.0 the program updates provisional read-back status handling in the fixed-mapping verification module while retaining the unqualified supported status requirement for verified export. A separate conditional short-acquisition path wraps the standard estimator; the MS reader now recognizes documented comma-filled MassHunter footer padding, and the explicit New Wave reader preserves line/spot event semantics. Standard long-acquisition numerical behavior is checked against the grating example.

An explicitly mapped numeric MS CSV that fails the strict reader because of missing signal values can still receive a raw inspection timeline. Finite values are drawn, nonfinite regions remain gaps, and original record numbers are listed in `input_processing.json`. No rows are removed for diagnosis: the run remains an input error (exit 1, INCOMPLETE) and cannot publish a correction. Unknown mappings or invalid time coordinates are not guessed.

Input or published-byte changes remain integrity errors: exit 1 and `INCOMPLETE.json` invalidate the run. A drawing failure also returns 1 and writes `preview_error.json`; when unchanged original MS data remain readable it supplies a clearly labelled raw-signal fallback. That fallback is not a successful corrected reconstruction.

`report.md` and the line that `run` prints at the end state the single-pass rate together with the standard error of its slope. The rate after iteration is stated without a standard error, because the standard error in the report belongs to the single-pass fit. For each check that is not met, `report.md` gives the measured value and its limit where the report holds them. `notes` in `report.json`, repeated in `report.md` and in the printed line, says when the record has too few firing intervals, when the iteration did not converge, when no provisional log was written from the estimate and whether a supplied reference rate was used. The printed line adds that an uncorrected inspection view is available once the preview has been drawn. When a signal column or a sample selector is not found, the error message lists the columns or the sample names of the file. See [QUICKSTART.md](QUICKSTART.md) for these texts.

The package contains raw-data readers, the block-lag estimator, acquisition-level diagnostic checks, corrected-log export and readback, iolite ESL formatting, and a default visual inspection output. Passing the checks describes internal timing evidence; it does not establish independent spatial accuracy or identify the physical cause of drift. The program does not launch iolite or HDIP.
