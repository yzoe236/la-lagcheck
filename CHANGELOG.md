# LA-LagCheck 0.8.0

This release restricts provisional output, accepts the tolerance as a distance along the scan, and states more in the report and in the documents. The reference correlation core, the block-lag fit, the fourteen diagnostic checks, their thresholds, the statuses and the exit codes are unchanged. A verified corrected log is written under the same conditions as in 0.7.0. The eligibility described below restricts provisional output only: it does not withhold a supported result from the verified path, and a verified log still requires the read-back of the written file to pass.

- Provisional export eligibility. The rate estimated from an acquisition is written to a provisional log only when it is eligible. In 0.7.0 a provisional log was written whenever a rate was available. `provisional_export_eligibility` in `report.json` records the assessment for the diagnostic that an export uses: the adopted input-placement retry, otherwise the main diagnostic. An estimate is withheld in three cases. The single-pass rate lies within its screening half-width of zero (`rate_direction`). The single-pass rate, the candidate rate and the rates of the alternative settings differ in sign (`sign_across_settings`). The iteration did not converge and the rate still changes (`unconverged_iteration`). In each case the lag change over the firing span must exceed the tolerance of the run. `status` is `not_blocked`, `withheld`, `not_assessable` or `no_acquisition_rate`. A negative rate alone does not withhold an estimate. `not_blocked` means only that none of the three conditions was triggered.
- Missing quantities. If a required quantity is unavailable and no assessed condition withholds the estimate, the status is `not_assessable`, and the estimate is then not written. A missing quantity is never read as zero. An alternative setting that gave no rate makes `evidence_completeness` `incomplete`. Missing alternative estimates alone do not withhold an otherwise eligible provisional export; all other eligibility and export requirements still apply. The missing settings are listed in the report.
- When an estimate is withheld, no provisional log is written from it. The estimate and the failed checks stay in the report, and the exit code stays 2. A reference rate given with `--reference-rate-ppm` is then written instead, as a rate-only mapping that takes no fitted constant from the estimate. In 0.7.0 a reference rate was used only when no rate could be estimated.
- The preview and the log read one record of the mapping in use (`applied_mapping`). A withheld estimate is not drawn as an applied correction. It appears in a separate panel whose title starts with `rejected candidate for inspection`, and the uncorrected inspection view is still drawn when no rate is applied. The rate source and the read-back status on the preview are those of the file that is displayed. The failed read-back of an earlier candidate is stated separately.
- After a failed read-back, the checked candidate is published as a provisional log only when the estimate it was written from is eligible. Otherwise the candidate stays in the run directory for diagnosis only.
- The notes of a provisional log to which warnings apply end with one sentence that points to those warnings. The notes of other provisional logs are unchanged.
- Tolerance as a distance. `analysis.tolerance_um` or `--tolerance-um` gives the tolerance in micrometres along the scan. It is converted to seconds once, before the diagnosis, from the original laser log, with the largest scan speed of the valid firing intervals. The estimator, the checks and every read-back use that value in seconds. `--tolerance-s` replaces the tolerance of the configuration for one run. Giving both units in the configuration, or both on the command line, is an input error. `tolerance_resolution` records the request, the speed and the resolved seconds. The `config.json` of such a run holds the resolved seconds with this record, so a rerun and `iolite-export` do not convert again. A configuration that holds this record cannot be read by 0.7.0. `analysis.tolerance_s` still has no default.
- A scan speed is read from the laser log at each firing start only. A value that the firing start takes from an earlier record is used only when the recorded positions of that firing interval do not contradict it by more than a factor of two; without positions for that interval it is not used. This factor is a coarse screen and does not show that a speed is correct. `distance_scale.speed` counts the firing intervals by where their speed was written and by the reason a speed was not used. A distance is refused for spot records, for New Wave logs and when a scan speed is not usable for every firing interval. A tolerance in seconds is accepted for all of them. For a record that is split into fragments, each fragment converts the distance with its own speed, and `segments.json` lists the resulting seconds.
- `distance_scale` in `report.json` and a new section of `report.md` give the time differences of the diagnosis as distances along the scan when a scan speed is known. Spot widths are given only when the width of the spot along the scan is declared with `analysis.spot_width_along_scan_um`, or when the log records a spot that leaves no choice: a circle, or a square with its sides along the stage axes that is scanned along an axis, unchanged during each firing interval.
- Report texts. `report.md` and the printed line state the single-pass rate with the standard error of its slope and name the kind of rate that is reported. For each check that is not met, `report.md` gives the measured value and its limit where the report holds them. `notes` says when the record has too few firing intervals, when the iteration did not converge, when no provisional log was written from the estimate, and whether a supplied reference rate was used (`reference_rate`). When a signal column or a sample selector is not found, the error message lists the columns or the sample names of the file. `--no-sample-label` leaves the sample label out of the title of the preview.
- Documents. `TROUBLESHOOTING.md` says what counts as an independent basis for a declared starting alignment, what a provisional log can be used for and which entries of the report to read before using it. It also covers the cases in which no provisional log is written or a distance is refused. `README.md` starts with the commands for one complete run. `QUICKSTART.md` gives the expected output of its examples. The chromium-grating README gives the commands and the expected values of its two affine logs.
- pytest is listed in `requirements-reference.txt`, and the README gives the pytest command with its expected counts. `requirements-lock.txt` records every package of the validation environment. The tests write their temporary files to the system temporary directory.
- Under the default error settings of NumPy, a floating-point warning from blocks without a usable correlation peak is no longer printed, and no value changes.

Validation (`VALIDATION.json`): the software tests; the chromium-grating example and the R01 example, whose rates are those of 0.7.0; and a comparison with the 0.7.0 release on the study data, run on the same computer. For R01 to R28, the complete diagnostic results under four settings and two starting alignments, with the corrected inputs of R05, R07 and R14, are identical to those of 0.7.0 (248 result sets, every value). The command-line runs of R29, of the two clock-comparison scans, of the three short-record examples and of the original-file export of R05 (54 runs) give the same exit codes, statuses, rates, checks and CSV files as 0.7.0. Their records differ in two designed ways: the 72-interval example no longer writes a provisional log, because the direction of its single-pass rate is uncertain, and the notes of the provisional log of the 96-spot example end with the sentence that points to its warnings. With the default settings and automatic starting alignment, none of R01 to R28 is withheld. These outcomes are retrospective. They describe internal timing consistency and do not establish independent spatial accuracy. Validation entries of earlier releases are kept in `VALIDATION.json` under the release that produced them and were not repeated for this release unless it says so.

# LA-LagCheck 0.7.0

This release changes two defaults so that the program finds the record-start condition and the matching signal itself. The reference correlation core, the block-lag fit and the fourteen diagnostic checks are unchanged. With both new defaults switched off (`analysis.skip_record_edge_lines = false` and `ms.signal_selection = "sum"`), all 81 comparison runs (R01 to R28 under automatic and declared starting alignment, 56 runs; the corrected inputs of R05, R07 and R14 under both alignments, 6 runs; three settings for R29; and 16 settings for the two clock-comparison scans) equal the 0.6.0 default results.

- `analysis.skip_record_edge_lines` (default `true`). The diagnosis first uses every scan line. If a block's correlation peak lies at a search boundary imposed by the start or end of the signal record (in the initial fit, the iterated fit or any stability alternative), the whole diagnosis is repeated without the scan lines that start within 30 s of the first recorded sample, or end within 30 s of the last. The value 30 s is the largest lag-search half-width used in the checks. The same lines are left out of every fit of the repeated diagnosis; they are left out only if at least twelve lines per block remain. Coverage is still measured against all lines. The report has a `record_edge_lines` object (`enabled`, `applied`, `sides`, `skipped_at_start`, `skipped_at_end`, `guard_s`, `rule`). The reason is that in routine records the signal begins as the first line is fired, so the first block could not be shifted earlier and its peak lay at the record-limited search boundary, which failed the search-edge check; the neighbouring lines and the laser-off intervals between lines provide the missing signal on both sides. If no peak lies at such a boundary, the result is unchanged.
- `ms.signal_selection` now defaults to `"highest_alignment_peak"` for the CSV signal formats (netCDF keeps `"sum"`). `"sum"` can still be requested explicitly. The `config.json` written by a run names the columns that were actually used and sets `ms.signal_selection` to `"sum"`, so rerunning that file uses the same matching signal and does not select again. The comparison, the recorded candidates and the saved configuration are as described for 0.6.0.
- `analysis.exclude_record_boundary_blocks` is unchanged and remains off by default. It is the declared alternative when the search-edge check is still not met after the edge lines have been left out.
- `report.md` points to `record_edge_lines` in its section on record-boundary blocks.
- The R01 example now reproduces the figure with the default 0.7.0 analysis (Fe56 selected as the matching signal, automatic starting alignment, three scan lines at the start of the record left out, all ten blocks retained, status supported) instead of the declared record-boundary option. `reestimate_posthoc.py` is replaced by `reestimate_default.py`. `study_summaries/Supplementary_Data_S1.csv` was replaced by the table with the 0.7.0 default statuses and three added columns.
- The error messages and documents were updated for the new defaults. `examples/chromium_grating/expected_results.json` was regenerated for 0.7.0 with the same numerical expectations.

Validation (`VALIDATION.json`): the software tests; the chromium-grating example, whose automatic and declared rates are identical to 0.6.0 (its first line starts 22.68 s after the start of the record, so no edge line is left out); the original-file export rates of one acquisition (R05), identical; and the two iolite examples, identical. On the 28 saved-workspace acquisitions R01 to R28, with automatic starting alignment, a 0.2 s tolerance and the archived inputs, 18 are supported with the 0.7.0 defaults and none with the 0.6.0 defaults; 19 are supported with the saved alignment declared. Both defaults were chosen after the outcomes of these 28 acquisitions had been examined, so these counts are retrospective and are not a prospective success rate. They describe internal timing consistency and do not establish independent spatial accuracy.

# LA-LagCheck 0.6.0

This release adds a screen of the laser log and two declared options. The reference correlation core, the block-lag fit and the thirteen earlier diagnostic checks are unchanged: with default settings, rates, retained blocks and the results of those checks are identical to 0.5.0.

- Laser-log screen. Each line-change interval is compared with the median of up to five neighbouring intervals on each side. An interval is flagged when it differs by more than `line_change_limit_s` (default 1 s) and by more than ten times the scaled median absolute deviation of those neighbours. The result is reported under `laser_log_screen` and as the check `no_flagged_line_change_interval`. A flag marks an interval that is unusually long or short relative to its neighbours and does not establish its cause. A flagged interval withholds supported status; any estimated rate remains available. The screen was added because a timestamp step inside a block that then becomes unusable is not tested by the block lags, so an acquisition could pass every earlier check with such a step in its log. The new `screen-log` command screens the laser log of a run configuration without a signal file. Intervals that recur by design, such as bracketing standards, are flagged. Groups of similarly displaced adjacent intervals can escape detection because they shift the local reference. A changed limit is recorded in the report and in the manifests.
- `analysis.exclude_record_boundary_blocks` (default `false`). A record-boundary block has its lag search cut short by the start or end of the signal record and its peak within two sampling intervals of that shortened boundary. The report lists such blocks under `record_boundary_blocks` under either policy. With the option, a fully observed record-boundary block that would otherwise enter the fit leaves the fit and the coverage and must still agree with the fitted line. This agreement uses the measured peak near the boundary of the observable search range. It can show a lag inside the record but not a lag beyond the record boundary, which is the case the search-edge check guards against by default. The option therefore assumes that the record contains the signal of the excluded block; the report gives the peak of that block beside the median peak of the retained blocks. If the option excludes a block in any reported fit or stability alternative, a passing result has status `supported_excluding_record_boundary_blocks`, exits 2 and can publish only a provisional log. With the option set and no block excluded, the result is unchanged.
- `ms.signal_selection = "highest_alignment_peak"` (default `"sum"`). The option compares the configured sum and each configured column by the peak of the automatic starting-alignment search around the input placement and uses the candidate with the highest peak. The sum is kept unless a single column exceeds it by more than 1e-9. The search is the automatic one even when a starting alignment is declared, and a candidate can win on peak height without meeting the starting-alignment criteria; the report records both facts. The choice is recorded under `signal_selection`.
- `report.md` states the screen result, any record-boundary blocks and any signal selection.
- The R01 example now uses the built-in record-boundary option in place of its own replacement of the block measurement, with the same rate.
- Sample labels and wording that described the type or origin of samples, beyond the word biological, were removed from tests, comments and documents. The optional private test fixture is no longer named, and its expected sample label is read from the fixture. In the summary tables, matching signals of the biological samples name only C13 and Fe56. One comment in the reference correlation core was reworded; its code is unchanged.

Both options were defined after the default outcomes of the study acquisitions had been examined. Results obtained with them are retrospective and are not a prospective success rate.

Validation covers the software tests, the chromium-grating example (rates unchanged), the R01 example (rate unchanged) and a repeat of the study analyses recorded in the project release records. The screen detects anomalous intervals larger than its limit; it does not identify their cause, detect gradual clock-rate changes or guarantee detection of every timestamp discontinuity.

# LA-LagCheck 0.5.0

This local research-preview release adds explicit New Wave event-log parsing, conditional analysis for short line or spot records, and coordinate/timing inspection views. See NEW_WAVE.md for input selection, analysis conditions and reproducible commands. The original long-acquisition estimator and its reference thresholds remain available.

- Sequence/sample identity and original event record numbers are preserved. Repeated On events are audited as state updates. Spatial views use stated first-On/Off endpoint assumptions; stale intermediate coordinates and inherited positioning speeds are not treated as measured ablation trajectories or scan speeds.
- Short records report available, failed and unexecuted checks separately. Unverified automatic peak candidates are labelled as such, including when no rate can be fitted. A failed diagnostic does not suppress readable inspection views. Conditional corrected logs remain provisional.
- Iolite-compatible export can omit only zero-duration event pairs whose prior exclusion is tied to unchanged original input and provenance. It records every omitted row. It can materialize inherited sample/sequence labels before sorting while checking event membership, pairing and all other non-time cells. This does not claim actual receiving-application acceptance.

Validation includes the public otolith and gabbro examples, internal fixed-mapping readback of provisional logs when a rate exists, a chromium-grating control, and software tests. A 69-line sample-only otolith selection did not provide four usable blocks and therefore received inspection views without an estimated correction. Physical time-origin and spatial accuracy remain separate from successful parsing or plotting.

Candidate validation reports may display version 0.4.0 because the version metadata was changed only after the functional code was frozen. Project release records bind the unchanged functional source hashes to this 0.5.0 copy and record a fresh full-suite validation. No public repository upload or external publication is implied by this local directory.
